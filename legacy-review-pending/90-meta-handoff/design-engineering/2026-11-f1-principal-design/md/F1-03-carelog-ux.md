# F1-03 Carelog UX: 기존 화면 검수와 기기별 구조안

- 대상: `carelog-fe@963f173`(dev, PR #37 병합 뒤 = 토큰과 공통 UI만 적용된 상태). `pnpm build:e2e` 후 `vite preview`, 인메모리 fixture, 시계는 2026-08-11 12:00(KST)로 고정했다. 고객 이름(박세입, 최내원)은 저장소 fixture의 합성 이름이다.
- 화면 어휘는 "고객 / 일정"을 쓴다. 내부 도메인 명칭은 건드리지 않는다.

## 결론

1. **Host는 계약대로 동작한다.** 767/768에서 하단 내비 → 레일, 1179/1180(가로)에서 1단 → 2단. 세로 1180은 1단이다.
2. **화면 안은 아직 PR-1(토큰)만 들어간 중간 상태다.** 페이지 바탕이 흰색이고 회색 띠로 날짜를 나누며, 시각이 가장 작은 글씨로 오른쪽 끝에 있다. 업무 화면에서 가장 먼저 읽혀야 할 "언제"가 가장 약하다. 이게 필수 수정의 중심이다.
3. **폰에서 가장 큰 문제는 하단 내비 101px다.** 320×640에서 본문 높이가 539px라서, 실제 앱은 타임라인 첫 행이 잘리고 시안은 다음 일정 Key Block의 "일정 추가"가 첫 화면 밖으로 밀린다. 계정 줄을 탭 줄로 합치면 44px가 돌아온다. 제품 결정이라 D로 올린다.
4. **업무 기록(일정 상세)은 "오늘 끝낼 일 하나"가 분명한 화면이다.** 정리 필요 상태에서만 Strong "기록 완료"를 Key Block 안에 둔다. 하단 고정은 쓰지 않는다.

추천: 필수 M1~M6을 진행 중인 PR-2 이후 화면 PR에 넣는다. F1-G4(하단 내비)은 Owner 결정을 먼저 받는다.

## 4. 기기별 구조안 [시안: 새로 만든 HTML 렌더]

| 화면 | 폰 390 | 태블릿 세로 768 | 가로 1024×768 (가용 944) | 가로 1440 (가용 1360) |
|---|---|---|---|---|
| ④ 고객 목록 | 하단 내비. 카드 1장 안 행 4개 | 레일 80. scan 720 | 레일. 한 열 | 목록 + 선택 안내 |
| ④ 고객 상세 | 머리 → 맥락 → 다음 일정(Key) → 메모 → 타임라인 | 한 열 520 | 한 열 560 | 목록 + 상세(최대 640) |
| ⑤ 일정 | 주간 띠(고정) → 정리 필요 안내 → 날짜별 카드 | 같음, 720 | 같음 | 일정 + 선택 안내 |
| ⑤ 일정 추가 | 한 열 폼. Strong 전폭 | 520 | 560 | 일정 + 폼 |
| ⑥ 업무 기록(정리 필요) | Key Block 안 Strong. 확인 패널은 그 자리에서 펼쳐진다 | 같음 | 같음 | 일정(선택 행 표시) + 상세 |
| ⑥ 업무 기록(기록됨) | Key Block(실제 시각, 원래 예정) → 메모 → 정보. Strong 0 | 같음 | 같음 | 일정 + 상세 |

기기별 차이:
- 폰: 하단 내비가 항상 있어서 고정 하단 행동을 쓰지 않는다. 주 행동은 Key Block 안, 첫 화면 안에 둔다.
- 태블릿 세로: 레일이 생기고 한 열이 유지된다. 폭 1180 이상이어도 세로면 1단이다.
- 가로 1180 이상: 왼쪽에서 고르고 오른쪽에서 처리한다. 목록으로 돌아가지 않고 다음 일정을 고를 수 있어서 연속 처리에 맞다. 키보드 ↑↓ 이동은 제안이다(계약 없음).

화면 유형과 Key(`docs/02` §10.5): ④목록 = 목록(Strong 0). ④상세 = 업무 상세(Key: 다음 일정, "일정 추가" Subtle). ⑤일정 = 목록(Strong 0). ⑤추가 = 입력(Strong "일정 추가"). ⑥정리 필요 = 업무 처리(Key: 상태 + 시각, Strong "기록 완료"). ⑥기록됨 = 기록 상세(Strong 0).

**Strong 근거(세 질문)**: ⑥ 정리 필요 — 가장 중요한 하나인가(예: 지난 일정을 닫는 일), 그걸 하러 왔는가(예: 안내를 눌러 들어온다), 반복해 봐도 도움이 큰가(예: 닫으면 사라진다). ⑤ 일정 화면의 "+ 일정" — 둘째 질문이 "아니오"(훑어보러 온다)라서 Subtle.

## 5. 유지한 계약과 확인이 필요한 사실

| 항목 | 처리 |
|---|---|
| 상태 3개(PLANNED / OCCURRED / CANCELLED), 지남·준비됨은 PLANNED의 표현 | 유지. 시안의 상태 라벨: 예정, 정리 필요, 기록됨, 취소됨 |
| 취소됨은 원래 예정 시각을 보존하고 실제 시각을 만들지 않는다 | 유지. 타임라인에 "원래 예정 8월 12일 (수) 13:30" |
| 기록 완료는 실제 시각을 받고 예정 시각을 보존한다 | 유지. 확인 패널에 "원래 예정 시각 09:30은 기록에 보존돼요" |
| 기록 완료 확인은 인라인 패널, 취소 처리에 새 Dialog 없음 | 유지 |
| 취소 복구 계약 | 시안에 복구 버튼을 넣지 않았다. 현재 화면에서도 보지 못했다. 계약 원문 위치를 찾지 못해 **NOT_VERIFIED** |
| 하단 내비의 계정 기능 | 유지. 한 줄로 합치는 안은 F1-G4 |
| Dark 노출 정책 | 유지(노출하지 않음). 시안 Dark는 검증용 |
| "AI에게 물어보기", "미리 준비하기", "기록에 대해 질문" | 현행 라벨과 위치 유지. 강도만 낮췄다. `.anno`로 계약 확인 대기를 표시 |
| 고객 메모 섹션 | 규범 시안(`care-customer-d`)과 `docs/06` F2에는 있는데 현재 화면에서 보지 못했다. 데이터가 없어서인지 구현이 없어서인지 확인하지 못했다 |
| 검색·필터·정렬, 목록의 다음 일정·상태 | 넣지 않았다(계약 없음, 목록 응답에 데이터 없음) |
