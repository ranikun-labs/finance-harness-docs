## 1. 서비스 제공 범위

서비스가 제공할 수 있는 것은 아래입니다.

| 영역 | 허용 범위 |

예시 허용 답변:

- 외국인 수급이 하루짜리인지 누적 흐름인지
- 월말/분기말 리밸런싱 구간인지
- 실적 기대가 가격에 이미 반영됐는지
- 환율/금리 환경이 우호적인지

이 내용은 특정 종목의 매수·매도 권유가 아닙니다.

## 2. 서비스 금지 범위

서비스는 아래를 제공하지 않습니다.

| 금지 항목 | 설명 |
|---|---|
| 매수/매도 권유 | “사세요”, “파세요”, “보유하세요” 금지 |
| 목표가 | 특정 가격까지 간다는 식의 목표가 제시 금지 |
| 손절가 | 손절 가격 제시 금지 |
| 수량/비중 제안 | “몇 주 사라”, “30% 비중” 금지 |
| 종목 추천 | “이 종목 사라”, “급등주 추천” 금지 |
| 계좌연동 | 증권사 API, 계좌 조회, 보유종목 자동 수집 금지 |
| 자동매매 | 주문 실행, 주문 예약, 매매 자동화 금지 |
| 수익 보장 | 수익률 개선, 손실 방지, 승률 보장 금지 |
| 개인 맞춤 포트폴리오 조정 | 보유자산 기준 리밸런싱 지시 금지 |

금융위는 유사투자자문업자가 불특정 다수를 대상으로 개별성 없는 조언을 제공하는 범위와, 온라인 양방향 유료 회원제·개별 상담이 투자자문업 영역으로 규율될 수 있음을 설명합니다. 따라서 이 서비스는 사용자별 질문에 답하더라도 **매수/매도/가격/수량/시점에 관한 개별 투자판단을 제공하지 않는 구조**여야 합니다. ([fsc.go.kr](https://www.fsc.go.kr/?utm_source=chatgpt.com))

## 4. 위험 질문 대응 정책

사용자가 직접적인 투자 판단을 물으면 답변을 거절하고 체크리스트로 전환합니다.

| 사용자 질문 | 처리 |
|---|---|
| “지금 사도 돼?” | 직접 판단 거절 → 진입 전 체크리스트 |
| “팔까?” | 직접 판단 거절 → 보유/매도 전 복기 질문 |
| “목표가 얼마야?” | 목표가 거절 → 밸류에이션 체크 항목 |
| “손절가 얼마?” | 손절가 거절 → 리스크 기준 기록 질문 |
| “몇 주 사?” | 수량 제안 거절 |
| “급등주 추천해줘” | 종목 추천 거절 → 종목 선별 기준 설명 |
| “내 기록 봐서 뭐 해야 해?” | 행동 지시 거절 → 과거 판단 복기 질문 |

표준 응답:

```text id="5avldm"
직접적인 매수·매도 판단은 제공하지 않습니다.

대신 현재 상황을 점검하기 위해 아래 항목을 확인할 수 있습니다.

1. 이 판단은 단기/중기/장기 중 어느 관점인가?
2. 진입 또는 보유 이유는 실적, 수급, 가격 모멘텀 중 무엇인가?
3. 월말/분기말 리밸런싱 등 수급 이벤트가 있는가?
4. 이 판단이 틀렸다고 볼 신호는 무엇인가?
5. 지금의 감정이 판단에 영향을 주고 있지는 않은가?

이 내용은 투자 권유가 아니라 체크리스트입니다.
```

## 9. PolicyGuard 구조

PolicyGuard는 3단계로 둡니다.

```text id="qgy4a3"
Input Guard
  ↓
Generation Guard
  ↓
Output Guard
```

### 1단계: Input Guard

유저 질문에서 아래 의도를 탐지합니다.

```text id="b3dkuo"
매수/매도 판단 요청
목표가 요청
손절가 요청
수량/비중 요청
종목 추천 요청
계좌/보유분 기반 조언 요청
프롬프트 우회 시도
```

### 2단계: Generation Guard

LLM 프롬프트에 아래 원칙을 주입합니다.

```text id="n5x2jt"
매수/매도/가격/수량/비중/추천 금지
체크리스트 중심 답변
시장 사실 단정 금지
데이터 출처 없는 사실 주장 금지
기록/복기 CTA로 종료
```

### 3단계: Output Guard

LLM 응답에서 금지 표현을 검사합니다.

검사 대상:

```text id="dkxx2f"
사세요
파세요
보유하세요
익절
손절
목표가
추천합니다
몇 주
비중
수익 가능
손실 방지
```

금지 표현이 있으면:

```text id="whq7v6"
응답 차단
체크리스트 템플릿으로 재작성
위험 로그 저장
```

## 13. 보안/개인정보 정책

초기 보안 원칙:

```text id="ux60qf"
계좌연동 없음
증권사 API Key 저장 없음
OCR 없음
원본 증권앱 이미지 저장 없음
투자 기록 최소 수집
가격/수량 선택 입력
사용자 삭제 기능 제공
전송구간 HTTPS
외부 사용자는 opaque identity_user_id로만 참조
Credential/Token/Session의 Finance 저장 없음
민감 필드 암호화 검토
관리자 원문 접근 최소화
LLM 전송 전 민감정보 최소화
```

소유권/보호 구분:

| 데이터 | 처리 |
|---|---|
| `identity_user_id` | 외부 Identity가 부여한 opaque 식별자로만 참조하며 생성 규칙·Credential 구조를 해석하지 않음 |
| Finance Profile | Identity Account와 분리된 Finance Domain 데이터로 관리 |
| 투자 기록 본문 | 암호화 또는 DB 접근통제 |
| 가격/수량 | 선택 입력 + 암호화 검토 |
| Account, Password, Credential, Access Token, Refresh Token, Session | Finance가 소유·저장하지 않음 |
| 결제·구독 정보 | V1 미수집. 미래 Commerce 경계의 책임 후보 |
| API Key | 저장하지 않음 |

### Identity / Commerce 책임 경계

Finance Domain은 외부 사용자를 `identity_user_id`로만 식별한다.
Identity Account와 Finance Profile은 별개이며, Finance는 Account,
Password, Credential, Access Token, Refresh Token, Session을 소유하지
않는다.

Finance가 소유하는 것은 Journal, Question, Checklist, Review, Watchlist와
각 데이터의 `identity_user_id` 기반 소유권이다. 실제 외부 Identity
의존은 V1 이후의 별도 Backend Architecture 단계로 유예한다.

결제·구독은 미래 Commerce 경계의 책임 후보이며 V1에는 실제 Billing,
Payment 또는 결제 데이터 수집을 두지 않는다. 요금제나 Entitlement의
존재 여부와 관계없이 Finance PolicyGuard와 Output Validator는 모든
Finance 응답 경로에 항상 적용한다.
